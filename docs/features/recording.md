# 直播间、录制与弹幕

不再需要监控某个直播间时，可在直播间卡片上点击「删除」并确认。正在录制的房间需先停止录制并等待收尾完成。删除会停止开播守候并取消该房间的录制预约，已有场次、录像、弹幕和切片仍然保留；重新添加同一直播间会恢复原有身份与历史记录，但不会自动恢复开播守候或旧预约。

直播间卡片可直接选择「开播后自动录制并分析」，同时启用两个开关并解除人工暂停；只保存单独开关仍保留原暂停状态。服务运行时显示守候、启动、录制、等待下一场及检测错误，程序退出或系统休眠时不会检测。录制前获取最新标题，所有录制入口（含 CLI、手动录制）在运行中默认每 30 秒刷新，单次超时 3 秒；页面轮询后可见。失败保留缓存并标注“上次获取”。场次保留开录标题、观测到的变更与结束标题，旧场次没有历史证据时显示未知；渲染片头按素材时刻的场次观测取标题，不改写已有成片或稿件。每日/每周预约在启动失败或房间已录制时也只创建一个后继，房间需开启「预约录制」。

```powershell
# 在已下载并解压的 BiliLiveCut 项目根目录执行

# 按安装指南准备环境后，登记一个你有授权的直播间
blc add-room "https://live.bilibili.com/你的房间号" --authorize

# 查看 / 检查
blc list-rooms
blc check 你的房间号

# 开始录制（Ctrl+C 停止；默认值由 RECORDING_PIPELINE_ENABLED 控制）
blc record <db_id>
```

录制产物位于 `storage/raw/session_<id>/`。默认以 300 秒为分片目标；FFmpeg 按实际关键帧落盘，因此单片时长会在 5 分钟附近小幅浮动。

每场录制独立编号；同场断线重连继续原序号，新场次重新从 1 展示。转写与成品页面按场次分页浏览，新成品归档到 `storage/clips/session_<id>/`，历史文件保持原位置。

HLS 输入关闭 FFmpeg 的持久 HTTP 连接复用，避免初始化段读取失败后触发 `v->input` 断言；HLS 与 FLV 候选线路仍按原规则选择。初始化段失败、断流或进程崩溃会在既有预算内重新获取地址，已完成片段保留。崩溃诊断优先显示断言等致命尾部内容，并对地址、凭据脱敏。标题刷新仍使用 3 秒总预算，失败日志包含房间、来源、失败阶段与预算，保留此前标题及成功观测时间。

## 程序中断后的恢复

已接受的录制请求会持久保存。服务重新启动时，先确认旧录制进程已退出，检查已接纳线路的清单和尾片，登记可用媒体并结束旧场次，再核查当前房间授权、人工控制和平台直播状态。仍可恢复的请求开启新场次，原场次及素材保留；平台状态未知时等待复核，不根据缓存猜测开播。人工停止、暂停、已撤销授权或需要人工处理的错误会阻止自动恢复。

短时间连续异常中断最多自动恢复三次，实际稳定产出媒体后重置次数；耗尽后显示错误，处理原因并显式启动才能重新开始。正常关闭服务保留当时尚在录制的运行请求，之后重新启动时经过相同检查。录制预约在接受请求时一并登记为已处理，恢复不会重复消费同一次预约。该机制只处理具有本版本正式恢复记录的录制，不推断旧场次的运行意图。

尾片不可播放时保留原文件并记录原因，不登记为可用素材。若无法确认旧写入者已经退出，服务启动会失败并给出诊断；请先检查残留的所属进程和文件权限。删除锁文件不能代替退出确认。

## 开播事件守候

开启自动录制并确认授权后，内置 Bilibili 来源通过独立 WebSocket 长连接监听开下播事件。正常守候期间不再按固定间隔请求 B 站开播状态；首次连通和每次重连后补查状态，因此程序启动时已经开播、或断线期间错过通知，也能恢复守候。补查失败或状态未知时，按照「守候刷新与兼容轮询间隔」重试，同时遵守来源要求的等待时间；获得有效状态或收到新事件后结束旧补查。守候连接沿用登录优先、匿名回退、候选节点和心跳重连机制，不需要安装第三方 B 站 API 库。

带有效 `live_time` 的 `LIVE` 消息触发自动录制；连接期间不带开播时间的同名消息不作为一次新开播。`PREPARING` 表示下播或轮播，进入「下播收尾延迟」，延迟结束后再查询状态，并确认仍是原录制任务后才停录。停录复核失败或状态未知时，保留录制并按同一间隔重试；恢复直播的事件会撤销停录，旧复核不能停止替换后的录制任务。连接中断不会直接停止录制。人工暂停、授权、自动化开关，以及“等待下一次真实开播”的保护仍然生效。

补查与停录复核仅对临时故障和未知状态自动重试；认证、房间身份等永久错误会显示具体错误码，等待处理或后续连接重新建立。自动启动遇到临时故障时，监控器按守候刷新间隔重新应用最近的有效开播状态，无需等待另一条开播通知。重试仍检查授权、自动录制开关和人工暂停；新的下播通知或断线会取消旧启动重试，重连后先补查最新状态。

设置「采集弹幕」只控制录制期间的弹幕采集和保存，不关闭开播守候连接。守候连接不创建录制场次、不保存弹幕，也不调用采样器；录制启动后由原会话采集器按既有策略处理弹幕、礼物、醒目留言和进场互动。原始档仍在采样前保存收到的消息。

「守候刷新与兼容轮询间隔」用于刷新本地房间配置、回收已禁用的订阅，并为不提供事件能力的第三方直播源保留状态查询；它不控制 Bilibili 开播通知的速度。「下播连续确认次数」只用于查询型来源，事件型来源不要求重复收到多条下播通知。录制中的标题刷新仍独立按「直播标题刷新间隔」执行。

## 弹幕数据库与原始档

默认开启弹幕采集（设置中心的「采集弹幕」，对应 `COLLECT_DANMAKU`）。内置 Bilibili 来源无需另装直播源插件；能否接收消息取决于实际连接与平台限制，有 Cookie 时先尝试登录访问，失败按现有策略回退匿名连接。

数据库 `storage/blc.db` 的 `danmaku` 表继续用于分析，可能受密度采样影响。每场另存 `storage/raw/session_<id>/danmaku.jsonl`，在解析及数据库采样前保存收到的 Bilibili 消息；外部直播源插件保存校验后的公共事件。它记录已接收到的消息，不能补回断连期间的消息或旧场次。

### 每个直播间的入库保留规则

在「直播间」页面找到对应的 Bilibili 直播间，点击「弹幕保留」独立设置本房间的规则。已有房间未配置时沿用以下默认值：

| 消息类型或规则 | 默认值 |
| --- | --- |
| 普通弹幕保留率 | 30% |
| 礼物保留率 | 80% |
| SC 保留率 | 100% |
| 进场等互动保留率 | 100% |
| 高密度规则 | 开启 |
| 高密度阈值 | 1000 条/分钟 |
| 高密度普通弹幕保留率 | 10% |

比例支持 0%～100% 的整数，每项比例的 0% 表示该规则下不入库，100% 表示全部入库。开启高密度规则后，密度严格超过阈值时，普通弹幕改用高密度保留率；其他类型不受此阈值影响。如需普通弹幕始终全部入库，应将普通弹幕保留率设为 100%，并关闭高密度规则或将高密度保留率也设为 100%。密度沿用最近 60 秒的滑动窗口，按已识别消息的实际时间跨度折算，开始接收时也可能很快触发高密度规则。采样使用序号分桶，不按消息内容判断重要程度。

保存仅影响该房间之后收到的消息；录制中的采集器在下一批消息到来、且距上次读取规则至少 5 秒时刷新配置，无需重启录制。已入库的数据不会重采样。「恢复默认值」只修改表单，点击保存后才生效。

这些规则只控制分析数据库，原始 JSONL 仍在采样前写入收到的业务消息。上舰等当前未映射为数据库类型的消息仍只保存在原始档。插件来源保持其已有公共事件保存行为。

API 可通过 `PATCH /api/rooms/{db_id}` 的 `room_config.danmaku_sampling` 部分更新；概率使用 0～1、精度为 0.01，例如 `{"room_config":{"danmaku_sampling":{"gift_rate":1.0}}}`。未提交的采样字段、热词、别名与其他房间设置会保留。规则保存在原有房间配置 JSON 中，旧房间自动读取默认值，无需清空数据库。

### 原始档下载与保存

在工作台「弹幕」页选择场次，点击「下载原始弹幕（JSONL）」；也可访问 `GET /api/sessions/{session_id}/danmaku-archive`。录制中下载只包含请求时已写完的完整记录。每行含 `version`、`kind`、`session_id`、`platform`、`source_id`、UTC `received_at` 和 `payload`：`session` 是场次标识，`raw` 是 Bilibili 解码消息，`normalized` 是插件公共事件（含 `occurred_at`、`content`、`user_name`）。不写入连接鉴权包、Cookie 或宿主连接配置。

禁用采集或来源不支持弹幕时不生成文件。仅有场次标识不代表已成功连接或有弹幕，页面同时显示真实采集状态。磁盘或权限错误会显示写档失败并停止本场文件写入，数据库采集仍继续。每批写完即关闭文件；异常退出可能留下最后一条不完整记录，下载会排除该行。原片自动清理只删除媒体分段，弹幕原始档单独保留；请按需要归档或清理。

## 自动化开关

五个独立开关，可自由组合：

- `auto_record` — 自动检测开播并录制
- `auto_analyze` — 自动转写 + 高光分析
- `auto_render` — 自动生成切片
- `auto_approve` — 高分候选自动批准
- `auto_upload` — 自动提交上传

每个开关逐阶段独立判断，修改后未完成任务按新配置执行。支持房间级别配置覆盖。

等待自动分析、相邻分段或人工审核的调度日志按阶段汇总原因和数量，仅在状态变化时记录；关闭自动批准时任务保持待审核。缺少事件关联的警告保留最多三个任务编号用于定位。

Portable Web 控制台可在“设置中心 → 房间自动化与端口”中按直播间独立修改上述五项开关；预约录制、阈值自学习、弹幕情绪与审核阈值也集中在同一页。房间级 `auto_upload` 需配合设置中心“上传与发布”分类的两个全局开关，并达到房间自动投稿分数阈值。

## 断流重连与登录回退

断流或平台暂时无法返回播放地址时，录制器按 `RECORDING_RECONNECT_MAX_ATTEMPTS`（默认 20 次）及 `RECORDING_RECONNECT_MAX_ELAPSED_S`（默认 180 秒）控制每轮连续故障。计时从取流尝试开始，包含取流、候选竞争及退避等待；取流和等待使用剩余期限。正常媒体持续推进时不会因超过该故障时限而结束健康录制。同一连接已登记媒体累计达到目标分段时长后，立即重置次数、计时与退避；跨失败连接的短末片不累计为稳定恢复。任一预算耗尽后，本次会话按错误收尾并保留已有媒体和失败原因。将某一项设为 `0` 可单独禁用该限制；两项都设为 `0` 时仍保留 20 次安全上限。

启用自动录制的房间在预算耗尽后进入冷却，时长取 `RECONNECT_MAX_BACKOFF_S` 与 `LIVE_POLL_INTERVAL_S` 的较大值，默认 30 秒。冷却结束后复核平台状态，明确仍在直播时通过原授权和人工控制检查启动下一次录制，无需等到另一条开播事件；每次录制继续遵守同样的有限预算。查询失败或状态未知时保留错误并限速复核，明确下播则等待下一次开播。人工暂停、人工停止、磁盘/权限/FFmpeg/配置和来源认证等永久错误不会自动恢复；处理原因后手动启动或显式重新开启自动录制。HTTP 403 不直接解释为 Cookie 过期。页面分别显示重连、收尾、冷却、人工暂停与需要处理的状态。

录制过程中还会监测当前连接输出的 TS 字节增长，以及并发胜出进程的媒体时间推进。连续 `RECORDING_STREAM_RACE_TIMEOUT_S`（默认 30 秒）没有推进时，仅回收当前所属进程树，再按预算刷新播放地址；正常长分片不需要等到完整分片落盘才证明录制仍有进度。空文件、文件时间更新、重复进度记录及其他连接的输出不能延长该计时。明确下播和人工停止按正常停止处理，空取流列表、干净 EOF 和事件连接断开本身不能证明下播。

`COLLECT_DANMAKU=true` 时，录制器会按 Bilibili 直播网页的 WBI 请求格式获取短期弹幕 token。有已保存 Cookie 时优先使用登录请求，并以 Cookie 中的 `DedeUserID` 完成 WebSocket 鉴权；登录请求失败或登录鉴权被拒绝后，会尝试不带 Cookie、`uid=0` 的匿名链路。DNS、连接、读取及鉴权回复超时、无效协议帧不消耗 Cookie 失败次数，也不触发 Cookie 失效通知；匿名连接存活期间，程序仍按 `DANMAKU_LOGIN_RETRY_INTERVAL_S` 定时探测登录链路，恢复后切回登录。HTTP 403/429/412 和业务 -352 保持风控/限流等待，尊重 `Retry-After`。业务 -101/-412、明确的非零 WebSocket 鉴权结果，以及实际携带 Cookie 的 `getDanmuInfo` 请求收到 HTTP 401，计入登录拒绝。HTTP 401 表示鉴权被拒绝，不直接判定 Cookie 已过期；公开接口、WBI 和匿名请求的 HTTP 401 不消耗 Cookie 次数。单场累计登录拒绝达到 `DANMAKU_LOGIN_RETRY_MAX_ATTEMPTS`（默认 5 次，首次计入）后，本场不再发送 Cookie。将最大次数设为 `0` 可始终匿名采集。

登录探测遇到 HTTP 404 等不可重试错误，或 WBI 请求收到 HTTP 401 时，会记录原因并停用本场登录探测，继续消费可用的匿名连接。匿名接口本身遇到 HTTP 401 或其他不可重试 HTTP 错误时，本场弹幕采集停止并显示失败；视频录制继续。

弹幕节点发生网络故障后，60 秒内优先尝试其他节点；所有节点仍保留为候选，到期恢复服务端顺序，鉴权成功后清除该节点的惩罚。同类连接故障首次或类别变化时告警，后续重复保留调试记录；连接恢复时记录一次汇总。连续连接失败达到三次时通知一次；登录拒绝、Cookie 过期各自去重，真实登录鉴权恢复后允许再次提醒。文件句柄或内存等本地资源耗尽会停止采集并保留错误，不作为节点网络故障继续轮换。

房间标题刷新默认等待最多 8 秒；失败保留最后可信标题和观测时间，并按配置间隔指数退避，通常最多 600 秒。配置间隔本身更长时保留该间隔，上游要求的更长 `Retry-After` 同样有效。重启后继续使用已保存的重试时刻；来源重绑后，旧请求的迟到结果不能覆盖新房间资料。详情接口失败不使已取得的开播状态失效。
