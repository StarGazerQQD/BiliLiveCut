# main CI 设置交互检查超时修复

本轮由五分钟监控发现，基于 main `25ea150c2e28b8e6412761ef4e76768a480ad41b` 创建修复分支。版本仍为 `v0.1.18.2-Alpha`，用户原有 `.tmp`、`.env`、数据库和媒体保持原状。

## 失败证据与改动边界

[main CI 的 Windows / Python 3.11 作业](https://github.com/StarGazerQQD/BiliLiveCut/actions/runs/34202336953/job/101983827819) 在 `tests/unit/test_frontend_javascript.py` 运行 `node scripts/check_configuration_interactions.mjs` 时超过 30 秒，抛出 `subprocess.TimeoutExpired`。该作业为 **1 failed、1,195 passed**，覆盖率 74.64%；没有报告设置业务断言失败。

本机原脚本连续运行 10 次均通过，用时 0.156～0.188 秒。原日志没有保留子进程阶段输出，因此无法确认当时卡在 Node 启动、文件复制、模块装载还是目录清理，也没有证据把原因归于杀毒软件、文件锁或产品死锁。

只读检查确认 `configuration.js` 仅依赖 `common.js`，两个模块没有在该路径启动后台轮询或未释放定时器；测试中的延迟读取、延迟保存均显式释放。原检查却为装载这两个模块创建系统临时目录、复制全部 15 个 JS 文件、写入 package.json，结束时再递归删除。

此次移除这一不必要的文件系统写入边界：读取两个真实模块，通过 data URL 在内存中装载，只替换唯一 `common.js` 导入地址，先严格校验匹配次数为 1。产品源码、业务断言、真实 fetch 替身边界和 30 秒超时均保持；独立模块图检查继续验证应用实际的相对导入关系。新增禁止 `mkdtemp/cp/copyFile/mkdir/writeFile/rm` 的运行场景，防止重新引入临时目录依赖。超时仍判失败，并保留 stdout/stderr 中的装载与断言阶段信息。

没有增加自动重试、延长超时、屏蔽检查或修改产品配置逻辑。当前证据证明了不必要的临时目录依赖已消除，不能保证消除所有宿主调度或进程启动超时；后续真实 CI 结果仍需独立核对。
