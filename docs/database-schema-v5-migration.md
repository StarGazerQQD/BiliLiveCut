# 数据库 Schema v5 升级与回滚

0.1.18 首次启动时只支持一条自动升级路径：未修改的 0.1.17.x Schema v4
升级到 Schema v5。升级会新增 `hotspot_events`，原有房间、录制场次、原始
分段、转写、候选、审核状态和成品记录保持不变。

## 启动前提

- `schema_meta.schema_version` 必须为 `4`；
- `schema_meta.app_version` 必须是 `0.1.17.x-alpha`；
- v4 模型指纹、表、字段、唯一索引和外键必须与正式版本完全一致；
- 版本更旧、手工改表或指纹不匹配时拒绝启动，不会猜测性修复。

## 备份与提交语义

迁移先使用 SQLite Backup API 创建 WAL 一致性备份：

```text
<database>.schema-v4.bak
```

备份经过 `PRAGMA integrity_check`、来源版本、来源指纹及“尚无
`hotspot_events`”校验后才会执行建表。通过校验的已有备份会复用，不会被
静默覆盖。

建表和 `schema_meta` 更新在同一数据库事务内执行。由于 SQLite DDL 在部分
驱动路径上可能先于事务提交，异常时程序还会精确删除本次新增表、恢复原 v4
元数据并再次做完整性检查。补偿回滚成功后可以直接重启重试；迁移前备份仍会
保留。

## 人工回滚

若日志明确报告“迁移及补偿回滚均失败”，程序会拒绝继续启动并给出备份路径。
此时：

1. 完全停止 BiliLiveCut，确认没有进程持有数据库；
2. 另存当前数据库、同名 `-wal` 和 `-shm` 文件用于诊断；
3. 将 `<database>.schema-v4.bak` 复制为原数据库文件；
4. 仅在进程已经停止且诊断副本已保留后，移走原来的 `-wal` / `-shm`；
5. 使用 0.1.17.x 打开回滚数据库，或修复环境后重新执行 0.1.18 迁移。

迁移成功后不会自动删除 v4 备份。确认 0.1.18 数据完整并另有常规备份前，建议
保留该文件。
