# 直播录制线路竞争与切换

录制器获取来源返回的所有候选地址后，先启动首选 FFmpeg，再以约 250 毫秒间隔增加候选，最多同时运行 4 路。
首选快速就绪时不再启动其余候选；明确失败时立即补位。优先覆盖不同主机或播放格式，再尝试编码变体。
同一画质内，视频包计数与媒体时间在多个进度报告之间推进至少半秒的进程胜出。
FFmpeg 6.1 等版本在流复制时不报告帧计数，此时还会使用现有 ffprobe 核验当前候选的本地 TS，
确认含至少半秒的视频包才判定就绪；探测不重新连接 CDN，且有包数、频率和超时限制。
单个大时间戳或只有音频推进不满足条件；发生时间戳回退时重新建立观察基线。
只有当前画质的所有候选都失败，才尝试来源排序中的下一档画质。
这里的“最优”表示优先候选中最快正常出流的一路，不保证长期带宽或稳定性最优。

胜出的 FFmpeg 进程继续写入原文件，不再交给另一个进程重新连接 CDN。
落选进程被终止并等待回收，同时排空管道，然后逐个清理其唯一前缀的 TS 文件和 CSV 清单。
交接前停止或失败时，未交接候选的文件也会回收。胜出线路录制结束后，先停止清单监听并补登记末片，
再删除该线路的 CSV 清单；有效 TS 录像仍按原有保留策略管理，登记失败时保留清单供排查。
删除遇到文件占用会在收尾时最多尝试 3 次；仍失败会记录文件名和系统错误码。
清理只识别本次生成的精确片段名与清单，不递归删除、不跟随符号链接。
断电、强杀整个应用后留下的历史文件无法仅凭文件名确认归属，因此不会按目录通配删除。
交接前再次检查胜出进程和管道；若已经退出，则进入下一轮取流，不把失效句柄交给录制器。
只有胜出者会启动分片清单监听、登记原视频并触发分析；竞争者不会产生数据库片段和下游任务。
停止、取消、磁盘保护以及进程创建期间的取消也会回收所有候选。

配置可通过环境变量或设置中心“全部参数”调整，下次录制生效：

| 环境变量 | 默认值 | 效果 |
| --- | --- | --- |
| `RECORDING_STREAM_RACE_PARALLEL` | `4` | 同时拉流的上限，范围 1–16；1 使用串行回退 |
| `RECORDING_STREAM_RACE_TIMEOUT_S` | `30` | 候选首次出流及录制中无媒体推进的最长等待，范围 3–120 秒 |

选线期间会短暂接收多路视频，所以并发数有上限；胜出后仅保留一路。
通过 FFmpeg 的 [`-progress`](https://ffmpeg.org/ffmpeg.html#Generic-options) 判断实际出流，
HTTP 200 或单纯建连成功不视为就绪。每条候选、整轮竞争均有超时。
[`-c copy`](https://ffmpeg.org/ffmpeg.html#Streamcopy) 不进行画面解码，因此就绪表示已经持续写出视频包，不能据此保证画面内容完整无损。
单条输入的参数错误或 HTTP 权限拒绝允许其他线路继续竞争；本地磁盘、输出权限或进程启动故障才中止整轮。
断流重连的次数上限按录制尝试轮次计算，时间预算也约束轮内的线路竞争。
从取流开始计时，稳定媒体登记后立即重置；健康媒体持续推进不受故障预算的总寿命限制。
两项预算都禁用时，一轮竞争仍最多 180 秒。

断流后重新获取最新地址并重新竞争，不复用旧签名 URL；过期地址由来源注册表过滤。
同一线路按服务器、端口、协议、容器、编码、画质识别，签名或路径变化不清除短期失败记录。
上述粗粒度标识仅用于短期排序，去重则比较完整候选及请求头；同主机不同播放路径仍能分别尝试。
失败记录只在当前录制器内存保留，5 分钟后过期；稳定产出达到目标分段时长后重置。
串行模式仍支持多 CDN 及 HLS TS、HLS fMP4、FLV 等格式轮换。
同一线路内的不同路径、查询参数或请求头也会逐个轮换，完整重复的端点不占用额外轮换位置。
每次重连仍使用本次新取得的 URL 和请求头；签名全部更新时按来源候选顺序延续轮换位置，
不会因刷新凭据而反复回到首条。组内还有未尝试端点时，同样缩短重试退避；原有总重试预算保持有效。

日志中的“并发录制选线”“录制候选失败”“录制线路胜出”显示选择过程。
胜出日志含进程 PID 和 `reuse=True`，不记录完整播放地址或请求头。
Windows FFmpeg 的网络读取错误 `-138` 会归类为网络异常。

## 兼容与回退

不提高上游的 Python 或 FFmpeg 版本要求，不修改依赖清单、锁文件、Docker 构建或来源插件契约。
竞争只额外使用已有多年的 `-progress pipe:1`，保留默认报告周期，不使用较新版本才支持的 `-stats_period`。
进度解析兼容 `out_time_us`、旧版 `out_time_ms`（实际单位也是微秒）以及 `out_time` 时间字符串。

若 FFmpeg 明确报告不支持 `progress`，先回收所有竞争进程，再沿用原有单进程命令录制。
本次录制后续重连保持串行模式，仍会重新获取地址并轮换线路；其他参数错误不会触发这一兼容回退。
可主动设置 `RECORDING_STREAM_RACE_PARALLEL=1` 使用串行模式。
进程启动遇到文件句柄、内存或进程额度不足时，复用已有的本地故障收尾流程，不作为 CDN 网络故障不断重试。

此功能不增加模型或收费 API 调用。所有线路都不可用时仍会失败，断流期间的视频不保证可补回。

## 选型依据

保留 FFmpeg 竞争与进程复用，适合当前“FFmpeg 录制、宿主登记分片”的结构。
单独进行 HTTP/ffprobe 探测后再启动 FFmpeg，需要重新建立拉流会话；引入本地代理转发已打开的输入，
则需要额外处理 HLS 播放列表、初始化段、媒体分片与请求头的转发，扩大维护范围。

错峰调度借鉴 [RFC 8305 第 5 节](https://www.rfc-editor.org/rfc/rfc8305.html#section-5) 的竞争思路，
但这里的成功条件是应用层媒体进度，非 TCP 握手，也不声称实现该 RFC。
并发上限为每个直播间的上限；同时录制较多房间时，可按服务器资源调低配置。
本功能优化启动与故障恢复速度，不持续后台测速，不以启动最快推断长期稳定性最优。
