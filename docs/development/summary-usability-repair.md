## 设计要求

### P1：整场总结

1. 生成前同时检查模型容量、结构化请求字节限制、候选预留空间和工作流最低请求数；预算不足必须在不可能完成的计划发送前说明。
2. 保留全场有序上下文综合；大输入沿用现有分层处理。核验按段落或事件分批，使用程序提供的稳定原文编号，不要求模型手抄长引用。
3. 持久化隔离草稿和逐批核验状态；完成的部分及原授权额度可恢复，回队或重启不刷新额度。
4. 对有具体不支持事实的正文定点修订后再核验；格式修复和正文修订分别记录，仍受同一总预算约束。
5. 正文与核验状态分开展示。未核验草稿不冒充已核验结果，草稿保存也不能替代正常素材完成自动核验的验收。

### P2：事件理解

1. 解释、事实核验、编辑判断共享同一材料快照；扩展上下文后重算失效结论。
2. 明确区分前文、后文、两者及证据不可用；实际没有材料时保留缺失原因。
3. 先确定实际候选边界，再判断其自身是否完整；需要的前后文必须进入实际媒体范围。
4. 保留人工保护、真实时间、媒体可用性及发布授权约束，兼容现有结果与界面。

## 验证与交付边界

- 覆盖长输入、跨午夜、录制缺口、超过 32 条依据、512 KiB 边界、多节点预算、非法 JSON、错引、不支持事实、恢复和额度不足。
- 覆盖依赖前文、依赖后文、无需上下文、ASR 缺失、扩展边界不可应用及片外证据不能证明片内完整。
- 测试在正式开发解释器及隔离数据库运行，不连接生产应用或实际模型端点。
- 新真实模型复验须先完成离线准备，明确材料、模型、请求数、token 与费用范围后取得独立授权；历史已关闭额度不能借用。
- 提交、推送和创建 PR 已由本聊天明确授权；只允许中文正常追加提交，不改写历史、不合并、不移动标签或发布。
